## Decisions

For #4, keep the persistence stack deliberately small and use what the project already has: **Polars + DuckDB**.

- Parquet will be the durable store for curated/derived analytical datasets.
- DuckDB will act as local catalogue/query/control storage: views over Parquet plus small metadata tables such as snapshot catalogue, schema metadata and DecisionRun records.
- Do not duplicate canonical fact rows into DuckDB merely for convenience.
- Do not add PyArrow pre-emptively. Add it only if a focused compatibility or round-trip test demonstrates a concrete gap in Polars + DuckDB.
- Preserve snapshot-grain history rather than destructively replacing current state.
- Use explicit tabular schemas and provenance rather than arbitrary Pydantic serialization.
- Generated Parquet should be written to a temporary sibling path, reopened/validated, atomically promoted, and only then registered in DuckDB.
- Reuse #3's raw snapshot convention exactly; do not create another raw-data layout.

The detailed implementation guidance and OSS reconnaissance are recorded on #4 rather than duplicated here.

## Risks / open questions

The main technical risks to prove early in #4 are type and provenance fidelity rather than scale:

- UUID round-trip representation;
- timezone-aware datetime round trips;
- Money/tenths representation;
- nullable optional fields;
- deterministic `*_latest` view selection without losing history;
- failure atomicity: a failed write must not leave a registered partial dataset;
- schema-version rejection behaviour.

PyArrow remains a deliberate fallback if these tests expose a genuine metadata/type limitation, not a default dependency.

The official FPL access position also remains intentionally conservative. #18 is closed because the research task is complete, not because automated extraction has been approved.

## Deferred deliberately

For #4, do not introduce Delta Lake, Iceberg, a general migration framework, hosted/cloud storage abstractions or a broader data-platform framework. They add complexity without solving the current local decision-engine problem.

## Issue #4 implementation findings

Issue #4 now provides the local persistence slice described above. Canonical teams, players,
gameweeks and fixtures are written as one immutable Parquet file per source snapshot below the
existing season-partitioned `data/curated` layout. DuckDB stores only catalogue, schema and
DecisionRun control metadata, with history and deterministic latest views reading the Parquet files
directly. The Issue #3 raw layout was reused without adjustment.

Polars 1.43 and DuckDB 1.5 handled every required round trip: UUIDs as canonical text, instant-valued
timestamps as UTC-aware microsecond timestamps, Money as exact integer tenths of a million pounds,
enums as their stable string values, relationships as UUID text and nullable fixture/source fields as
nulls. **PyArrow was not needed and no dependency was added.**

The write path uses a temporary sibling Parquet file, reopens it to validate its explicit schema, row
count and integer `schema_version`, promotes it without overwriting prior evidence, and only then
commits catalogue metadata and refreshed views in one DuckDB transaction. A failure removes files
created by that attempt and leaves no registered partial dataset. Unsupported future curated or
DecisionRun versions fail explicitly; rebuild-from-raw remains the evolution strategy.

One local driver quirk surfaced: fetching DuckDB `TIMESTAMPTZ` values as Python objects attempts to
load optional `pytz`. Control-table readers therefore cast timestamps to ISO text and reconstruct
aware standard-library datetimes, avoiding an unnecessary dependency; Parquet timestamps and SQL
time semantics remain timezone-aware.

The main follow-up risk is catalogue-view refresh cost as snapshot counts become large because each
view currently lists registered files explicitly. That is acceptable for the local first slice; measure
before replacing it with broader glob or manifest-driven discovery. There were no deliberate
deviations from the Issue #4 storage architecture or scope. Projection, optimiser, manager-state and
live-source work remain deferred to their own issues.

## Issue #5 implementation findings

Issue #5 now has two deterministic local-file adapters behind `ProjectionProvider`: the
project-owned generic CSV contract and the current `phase9_frontend_v1`-shaped FPL Forecast
contract. Provider selection lives in infrastructure configuration rather than application
conditionals, and neither adapter performs network access. No dependency was added and no AGPL
implementation or upstream forecast artifact was copied into the repository.

Identity resolution is deliberately exact. The generic provider requires an explicit external-reference
namespace. The FPL snapshot adapter now preserves optional upstream `element.code` as an additional
`fpl_code` reference, distinct from the season-specific element ID; FPL Forecast
`player_code_<code>` values resolve only through that reference. Missing and colliding references fail,
with no name/team/position fallback. A deterministic SHA-256 fingerprint covers the namespace and
full external-ID-to-canonical-UUID mapping, while a separate SHA-256 records the exact supplied CSV
bytes. Caller-supplied observation time, row generation time, season and provider version remain
explicit rather than inferred from file metadata.

The canonical projection corrections proved necessary: expected minutes are gameweek-grain and can
exceed 120 in double gameweeks; expected points and percentiles can be finite negative values;
appearance and start probabilities are separate; variance stays non-negative. For FPL Forecast,
`points_std` is squared into points variance, p10/p50/p90 map directly, and model variant plus
available xPoints/minutes/decision run IDs form deterministic row lineage. P(5+) and P(10+) remain
only in the referenced provider file because threshold probabilities are not percentiles. Missing
uncertainty remains `None`.

The main risks are upstream CSV schema drift and unresolved artifact reuse terms. Both are contained
by the user-supplied-file boundary, source hashing, strict required-field validation and the notice to
revalidate before adopting a newer schema. A future projections-persistence slice can store the
provider response provenance without changing the domain or resolver. There were no deliberate
deviations from Issue #5; model training, OpenFPL, automatic downloads, ensembles and optimisation
remain deferred.

## Issue #6 pre-implementation reconnaissance

Issue #5 is complete and merged into `develop`, so the first genuinely useful decision slice is now
#6: select a legal 15-player squad, XI and captain for one gameweek from canonical players and
projections.

The OSS reconnaissance was repeated immediately before implementation. `solioanalytics/open-fpl-solver`
is currently the strongest broad formulation reference: it is active in August 2026 and recently
moved its model construction to direct `highspy`. It models squad, lineup, captain, vice-captain and
bench choices plus substantially broader transfer/chip logic. It is not a suitable runtime dependency
for this project because it now requires Python 3.14, brings a much larger pandas/network-oriented
stack, and its Apache-2.0 licence text is accompanied by additional commercial-use language. Treat it
as an external formulation reference only; do not copy or vendor its code.

`daniel-mehta/fpl-forecast` provides a second useful, current 2026/27 reference. Its D1 decision model
uses a compact full-candidate MILP for squad, starters and captain with the same core legal constraints
we need. Its nominal objective is starting-XI expected points plus one additional copy of captain
expected points; expected points are already unconditional, so appearance probability must not be
applied again. The repository is AGPL-3.0, so this is also reference-only.

The implementation decision is therefore to own a thin `HighsSingleGameweekOptimiser` behind the
existing generic `OptimisationEngine` port, using the project's existing `highspy` dependency. The
primary objective is deliberately a transparent mean-only D1 baseline. It will enforce the canonical
15-player quotas, legal XI formation, £100.0m default budget, max three per club, squad/XI/captain
membership and bounded include/exclude/forced-player scenario constraints.

Bench quality must not distort the primary nominal score. Use a two-stage/lexicographic solve: first
find the globally optimal XI+captain objective, then among primary-optimal solutions improve selected
squad/bench quality without sacrificing that score. Vice-captain and bench ordering are deterministic
secondary choices on the fixed optimal solution: highest projected non-captain starter for vice, the
reserve goalkeeper in the GK bench slot, and outfield substitutes descending by expected points with
stable canonical-ID tie-breaking.

Appearance-aware automatic substitutions, captain non-appearance/vice fallback probability and
expected-realised scoring remain deliberately deferred. The first optimiser should be explainable and
serve as the exact baseline against which those later decision objectives are measured.

Validation should be synthetic and network-free. In addition to legality and scenario tests, add a
small independent brute-force/enumeration oracle test so the HiGHS formulation is checked against a
separate exact method rather than only testing its own output. The detailed implementation contract
and external-reference findings are recorded on Issue #6.


## Issue #6 implementation findings

Issue #6 now owns immutable, solver-independent single-gameweek request/result contracts and a
`HighsSingleGameweekOptimiser` infrastructure adapter. The model indexes canonical players by sorted
UUID and uses binary squad, starter and captain variables. It enforces the exact 2/5/5/3 squad,
legal XI formation, three-per-club limit, integer-tenths budget, membership implications and bounded
include/exclude/forced-player scenarios. `Player.active` is not interpreted as availability.

The objective is genuinely lexicographic. Stage one maximises unconditional XI expected points plus
exactly one additional captain copy. Stage two constrains that primary score to the optimum within
`1e-7 * max(1, abs(primary_objective))` and then maximises total selected-squad expected points. The
reported nominal score and HiGHS bound/gap remain the stage-one values. Vice-captain and bench order
are deterministic post-solve choices using expected points then canonical UUID; a forced vice is
also constrained not to become captain.

Preflight validation rejects duplicate/missing/wrong-gameweek inputs and contradictory scenarios. A
separate small HiGHS minimum-cost solve proves the exact cheapest legal squad under club, position
and scenario constraints before the budgeted primary model runs. Public failures use project-owned
codes and structured diagnostics; residual HiGHS status is preserved without leaking highspy types.
Full IIS extraction was not needed for this bounded slice.

HiGHS 1.15.1 accepted deterministic single-threaded, parallel-off and zero-gap settings. Its pybind
status enums must be compared by value rather than Python object identity. Re-solving the same model
after adding the primary-optimum band cleanly supported the second stage, and available stage-one MIP
dual bound/gap values survived into the canonical result.

The independent test-only enumeration oracle examined every legal squad, XI and captain in a small
synthetic universe and matched the HiGHS primary optimum exactly. The full suite remains synthetic
and network-free. No dependency or third-party code was added, and neither reference project was
incorporated, so `THIRD_PARTY_NOTICES.md` remains unchanged.

There were no deliberate deviations from the Issue #6 contract. Deferred risks are solver scaling
on the full future transfer/multi-gameweek model, richer infeasibility explanations beyond current
preflight/status diagnostics, and replacing the nominal bench policy with expected-realised autosub
logic only in a future explicitly scoped objective.
The implementation branch is `feature/6-single-gw-optimiser`.

## Issue #10 pre-implementation reconnaissance

Issue #29 changes the short-term priority: before GW1, manager-state and transfer mechanics in #7 add little value because the initial squad is still blank, while stale injury and availability information can materially change the team. The next implementation slice is therefore #10 on `feature/10-availability-evidence`, deliberately bounded to availability evidence rather than a general football-news or LLM project.

The existing FPL snapshot adapter already validates `status`, `news` and `chance_of_playing_next_round`, but currently converts them only into `Player.active` plus warnings; #6 deliberately ignores `Player.active` as an availability rule. The #29 real snapshot produced 76 such warnings, so Phase 1 can reuse information already present in the manually supplied local snapshot without adding another live-source integration.

The strongest implementation reference remains `daniel-mehta/fpl-forecast` (AGPL-3.0, reference only). Its current-season path retains status/news/news timestamps, chance-of-playing fields and selectability state, and its M7 minutes model already uses current availability to modify appearance/start probabilities before unconditional xPts are generated. That creates an important temporal rule for our architecture: the FPL Forecast xPts consumed by #5 may already embed the same availability evidence at the forecast timestamp. #10 must therefore model a **post-forecast evidence delta** and must not apply unchanged or older availability information a second time.

`fnhirwa/fantasypl` / FPLX (MIT) is a useful formulation reference because it separates per-player/per-gameweek news snapshots from deterministic signal interpretation and retains those snapshots for replay. Its keyword categories and numeric adjustment weights are heuristic, however, so there is no reason to add it as a dependency or copy its policy. `Jellman86/autoFPL` is useful as a research reference for point-in-time source semantics: publication, retrieval and availability times, content identity, contradiction handling and later walk-forward source evaluation. Neither project provides a component we should fork or vendor.

The Phase 1 decision is to own immutable canonical evidence and adjustment contracts, adapt the existing offline FPL snapshot as the first provider, preserve base `Projection` objects unchanged, and compare evidence timestamps with projection generation time. Definitive newer unavailability can become an explicit selection exclusion. Doubtful, returning or ambiguous evidence should change/surface start-minutes confidence and scenario warnings rather than use an arbitrary `xPts *= availability_factor` rule; current xPts is already an unconditional mean, so an uncalibrated multiplier would create false precision. Conflicting and stale evidence must remain visible.

External manager/press-conference collection and any LLM extraction/classification remain later #10 phases. The intended GW1 operational flow is: fresh local FPL snapshot plus latest forecast -> post-forecast availability delta -> exclusions/risk/scenarios -> #6 optimiser. The detailed reconnaissance and implementation contract are recorded on Issue #10.

## Issue #10 Phase 1 implementation findings

Phase 1 now owns immutable `AvailabilityEvidence`, `AvailabilityAssessment` and disposition contracts in the domain. The offline FPL-shaped adapter resolves season-specific element IDs through exact canonical external references and retains structured `status`, round-specific chance, selectability and removal fields plus unparsed news text. It preserves the snapshot ID and bootstrap SHA-256, a deterministic identity-mapping fingerprint, the source `news_added` publication time when present, snapshot observation time and adapter processing time. Missing `news_added` remains missing rather than being replaced by observation time.

Assessment is explicitly a post-forecast delta. Evidence published at or before `Projection.generated_at` is retained as already known and has no second decision effect. A caller-supplied staleness boundary can retain evidence without applying it. Contradictory latest evidence remains a conflict. Definitive newer unavailability is the only automatic Phase 1 exclusion; doubtful, indicative, ambiguous or unknown-time concerns require review, while positive return evidence does not boost points. ## Issue #7 implementation findings

Issue #7 now represents each owned player with exact purchase and selling prices and defines
ManagerState.free_transfers as the allowance remaining at the decision timestamp. The pure
selling-price rule uses integer £0.1m units: full losses are realised and half of a price rise is
retained with odd tenths rounded down. Transfers already made and previously committed points cost
are preserved, but the existing cost is sunk when assessing an incremental recommendation.

LocalFplManagerStateProvider maps a supplied FPL-shaped JSON file through an explicitly configured
canonical external-reference namespace. It validates supplied selling prices against canonical
current prices, rejects missing or ambiguous identities and chip-active states, and preserves the
file SHA-256, identity-mapping fingerprint, observed time and source reference. It performs no
network access.

The solver-independent transfer request/result contracts sit behind the existing generic
OptimisationEngine port. HighsSingleGameweekTransferOptimiser links final squad membership to initial
ownership and balanced transfer-in/out variables, enforces canonical squad/XI/club rules, and
calculates budget from outgoing selling prices plus incoming current prices. Stage one maximises
unconditional XI expected points plus one captain copy less four points per additional paid
transfer. Stage two preserves that optimum within 1e-7 * max(1, abs(primary_objective)) and minimises
transfer count. Stage three fixes both the transfer count and its exact paid-transfer consequence
before maximising final-squad expected points. This prevents a free transfer being spent only for
bench quality. Vice-captain, bench order and same-position transfer pairing use deterministic
expected-points/UUID rules.

The do-nothing squad is scored through the unchanged #6 mean-only optimiser, with its budget set to
the current market value of the already-owned 15 rather than the original acquisition cap. Expected
gain is the recommended net score after new hit cost minus that baseline. Existing hit cost is not charged
again. Normal next-Gameweek allowance is reported as
min(5, max(1, remaining_ft - transfer_count + 1)), including an explicit max_transfers=0 hold/roll
scenario.

Recommendation provenance reuses the existing DecisionRun and DuckDbDecisionRunRepository: manager
snapshot identity, projection versions, optimiser settings and target Gameweek are recorded. A
deterministic persisted summary identifies transfer-out and transfer-in IDs, transfer count, new hit,
expected gain and resulting bank; an optional explicit output reference remains available without
adding another persistence framework. The independent test-only enumeration oracle matched the HiGHS net
objective, transfer-count tie-break and final-squad objective.

There were no deliberate deviations from the Issue #7 contract. No dependency or third-party code
was added, and THIRD_PARTY_NOTICES.md remains unchanged. Chips, multi-Gameweek option value,
authenticated/live manager retrieval, transfer execution and a versioned recommendation artifact
remain deferred until a concrete consumer requires them.

## Issue #8 implementation findings

Issue #8 now owns immutable solver-independent multi-Gameweek request, per-Gameweek plan and horizon
result contracts plus a direct HighsMultiGameweekPlanner infrastructure adapter. The model jointly
indexes squad, XI, captain, transfer-in/out, bank and free-transfer state by player and Gameweek.
Every final squad carries into the next week; transfer balance, legal composition, club limits,
formation, captain membership and non-negative bank are enforced independently in every period.

Normal free-transfer rollover and paid hits use an exact finite-state formulation rather than a
relaxed approximation. For each week one explicit free-transfer/transfer-count state determines
paid transfers as max(0, transfers - allowance) and the next allowance as
min(5, max(1, allowance - transfers + 1)). Existing manager hit cost remains sunk. Stage one
maximises weighted unconditional XI points plus one captain copy less weighted new hit cost. Stage
two preserves that optimum within 1e-7 * max(1, abs(primary_objective)) and minimises total horizon
transfers. Stage three fixes transfer count before maximising weighted squad quality.

Prices are frozen at the decision timestamp. A legacy-ownership state retains each initially owned
manager-specific selling value until first sale. A player bought during the plan costs canonical
Player.price and, if sold later in the same trajectory, returns that same frozen value. Bank carries
forward exactly and receives no objective reward. Projection objects remain unchanged; geometric or
explicit Gameweek weights are strategy inputs, with discount_factor=1.0 representing undiscounted
cumulative net expected points.

The hold baseline keeps the original 15 and bank throughout the horizon, makes no new transfers,
rolls unused allowance to five and re-optimises only XI/captain through unchanged #6 semantics each
week. Horizon one matched #7 for transfers, squad, XI, captain, vice, bench, hit, bank, objective and
gain versus hold. Synthetic fixture-swing, delayed-transfer and multiweek-hit cases confirm the
planner is joint rather than a greedy loop. Later planned moves are conditional context; only the
first Gameweek action is intended for execution before replanning.

DecisionRun persistence reuses the existing repository and records the manager snapshot, projection
versions, horizon, target Gameweeks, explicit weights, transfer limits, frozen-price policy,
optimiser identity, first actionable transfer IDs and aggregate weighted gain. No arbitrary domain
blob or new persistence framework was added. The independent two-week enumeration oracle matched
the HiGHS primary objective, transfer-count tie-break and weighted squad-quality objective.

The exact unpruned 60-candidate CI diagnostic produced Optimal solutions in 0.063, 0.216,
0.831 and 1.583 seconds for horizons 1, 3, 6 and 10. A separate 587-candidate scaling diagnostic
used the same exact formulation and produced zero-gap Optimal solutions in 1.936, 2.754, 6.384 and
12.338 seconds, with horizon-10 size 41,250 variables and 46,269 constraints. Candidate pruning, time
limits and nonzero optimality gaps were not needed.

There were no deliberate deviations from the Issue #8 contract. Repeating the scaling measurement
with real multi-Gameweek projections remains a future operational check because those inputs are not
yet available locally. Chips, stochastic price scenarios, rival-aware utility, arbitrary
bank/free-transfer value, transfer execution and live manager retrieval remain deferred. No
dependency or third-party code was added, so THIRD_PARTY_NOTICES.md remains unchanged.
