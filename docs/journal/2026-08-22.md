# 2026-08-22

## Context

Issue #80 settled the control-plane architecture contract for Epic #73; Issue #81
(typed run-record provenance ledger) is the first unblocked implementation slice. The
operational problem it removes: Gameweek provenance was maintained by manual JSON
edits (`jq > tmp && mv` style), which is error-prone, non-atomic and lets invalid
stage/state transitions slip through. This session implemented #81 and its tests.

## What changed

- New typed `RunRecord` domain model (`domain/run_record.py`) encoding the #80
  invariants directly in validation: stage states PENDING/RUNNING/PASS/WARN/FAIL/BLOCKED,
  run states provisional/completed/failed/authoritative, append-only stage attempts,
  artefact references + SHA-256 hashes, recorded decisions, authority approval events.
- New `RunRecordRepository` port and error hierarchy (`ports/run_records.py`).
- New `RunRecordLedger` (`infrastructure/persistence/run_records.py`): one
  schema-validated JSON document per run under `state/run-records/`, written atomically
  (temp file + fsync + `os.replace`), with optimistic concurrency detection via the raw
  document snapshot the caller loaded. Legacy documents without `schema_version` are
  read best-effort: present fields parsed, absent fields stay absent, unparseable fields
  reported in `parse_issues`; nothing is fabricated.
- New `RunRecordService` (`application/run_record_service.py`) implementing the approved
  transitions, closure validation against the #80 definitions of completed/failed, and
  promotion with explicit attributable approval. Retries append new attempts and never
  rewrite prior ones.
- New `touchline` CLI (`touchline_cli.py`, `touchline` script in `pyproject.toml`) with
  `run-record` create/show/list/stage/artefact/decision/close/promote/validate commands.
- Tests: domain model invariants, service scenarios (all 12 required by #81 plus
  promotion/supersession/retry/legacy), ledger atomicity/corruption/resolution, CLI smoke.
- Dev-only `tzdata` dependency added: the existing Parquet round-trip tests panic in
  sandboxes without a system tz database (`ZoneInfoNotFoundError: UTC`); `tzdata`
  supplies the static database and is not a runtime dependency.

## Decisions

- **Previous-run authority**: explicit `previous_run_id` must reference a recorded run
  or creation is rejected with an actionable diagnostic. An omitted id deterministically
  resolves the current authoritative run for the same (season, Gameweek) — matching #80's
  "at most one current authoritative run per season/Gameweek" keying. Cross-Gameweek
  lineage therefore requires an explicit id (operator choice), not a heuristic chain.
  Resolution reads authority-event timestamps from document content; mtime/directory
  ordering is never used. Tied approval timestamps raise an explicit ambiguity error
  instead of guessing.
- **Completion semantics** follow #80 literally: completed requires every mandatory
  stage (declared on the record at creation) to have a terminal PASS/WARN latest attempt
  and no mandatory FAIL/BLOCKED remaining; failed requires mandatory execution to have
  failed. A run that is neither cannot be closed — it stays provisional rather than
  inventing an "abandoned" state.
- **Retry after PASS/WARN is rejected** with an actionable message. #80 permits explicit
  rerun of successful stages only where the stage contract is safely repeatable; whether
  a stage is repeatable belongs to the future DAG/orchestrator (#84), so the ledger
  refuses rather than choosing semantics.
- **Legacy vs v1** is distinguished by `schema_version`: absent -> legacy best-effort
  read; `1` -> strict validated read; `>1` -> `UnsupportedSchemaVersion`. Legacy records
  are readable but not silently migrated; mutations reject them and point the operator
  at recreating through the typed interface.

## Risks / open questions

- JSON-file ledger has no cross-process locking; concurrent edits by two processes are
  detected (read-modify-write compare) rather than silently lost, but the loser must
  retry. Fine for the single-operator local-first model; revisit if the orchestrator
  (#84) makes concurrent writers realistic.
- Same-(season, Gameweek) resolution scope could be re-read by the owner as "previous
  Gameweek". I implemented the literal pairing with the #80 per-season/Gameweek
  authority invariant; weekly chaining policy is 06.02's call. Flagged in the #81 handoff.
- `state` is stored and validated against history on every read, so hand-edited files
  that contradict their own history are rejected rather than silently repaired.
