## Implementation delivery

Three implementation slices were merged into develop on the same day, in a
deliberate delivery sequence where each layer depends on the previous.

### #81: Typed run-record provenance ledger

Replaced manual JSON provenance manipulation with a typed, validated, atomic
run-record interface. Key design decisions:

- **Previous-run authority** uses recorded authority events, never file
  modification time or directory ordering. An explicit `previous_run_id` must
  reference a recorded run; an omitted id resolves the current authoritative run
  for the same (season, Gameweek). Cross-Gameweek lineage requires an explicit
  id (operator choice).
- **Completion semantics** follow #80 literally: completed requires every
  mandatory stage to have a terminal PASS/WARN latest attempt; failed requires
  mandatory execution to have failed. A run that is neither stays provisional.
- **Retry after PASS/WARN is rejected** — stage repeatability belongs to the
  future orchestrator (#84), so the ledger refuses rather than choosing
  semantics.
- **Legacy vs v1** distinguished by `schema_version`: absent records are read
  best-effort with absent fields staying absent; nothing is fabricated.
- **Atomic persistence** via temp file + fsync + `os.replace` with optimistic
  concurrency detection.

Independent review: APPROVE WITH NON-BLOCKING FOLLOW-UPS. Concurrency and
authority-enforcement hardening deferred to #84.

### #83: Immutable Gameweek evidence identity

Implemented evidence identity as a typed v1 Gameweek manifest. Key design
decisions:

- **Semantic SHA-256** covers season/Gameweek, snapshot/provider identity,
  semantic source-as-of time, exact artefact byte hashes, projection content
  identity, forecast generation/effective time and only upstream lineage actually
  supplied.
- **Manifest formatting and key order are non-semantic**; source artefact
  whitespace is part of the exact bytes and therefore changes evidence identities.
- **Acquisition UUID and retrieval timestamps** remain separate provenance.
  Filesystem references locate immutable bytes for audit but do not enter
  semantic identity.
- **Atomic publication** uses the same-filesystem temporary-file plus
  hard-link/no-replace pattern. A concurrent identical winner is idempotent;
  a different-byte winner is rejected.
- **RunRecord schema v1** remains the exact historical #81 wire contract.
  New runs use schema v2 with optional `evidence_identity` binding.

### #82: Deterministic Touchline doctor diagnostics

Added a deterministic, read-only diagnostic suite validating the environment
before Gameweek runs. Key design decisions:

- **Release-isolation trigger**: detached HEAD at a recognised release tag
  marks an immutable worktree; branch checkouts at the same commit remain
  mutable. This resolves the Stage 6 path-resolution brittleness exposed by
  the GW1 rehearsal.
- **Missing state root / required dirs are WARN, not FAIL** — every writer
  auto-creates its roots, so a missing directory never breaks a run.
- **Existing-file consistency**: the state-root existence check mirrors the
  resolution check's verdict rather than emitting a misleading "does not exist"
  when the path resolves to an existing non-directory.
- **Centralised state-root resolution**: a single `_StateRootResolution` is
  shared across all three `paths.*` checks, eliminating TOCTOU and protecting
  against `OSError`/`RuntimeError` on invalid paths.

## Implementation boundaries

The control-plane implementation maintains separation between:

- **Decision evaluation** — existing `evaluate_decision()` and `OutcomeEvidenceV1`.
- **Lineup-evidence validation** — #91–#95 workstream, not yet implemented.
- **Control-plane implementation** — #81 provenance, #83 evidence identity,
  #82 doctor, with #84 orchestrator, #87 manager-state and #86 scenario
  lifecycle as future dependencies.

No evidence providers, forecast providers, optimiser, scenario lifecycle,
manager-state acquisition, orchestrator or submission planning was modified.

## Delivery sequencing

The implementation order was deliberate:

1. **#81** provides the provenance foundation (run records, stage tracking).
2. **#83** consumes the ledger interface for immutable evidence identity.
3. **#82** validates the environment against #80's state-root/path invariant.

The rapid delivery cadence was possible because each slice was architecturally
bounded with well-defined interfaces and consumed only the previous layer.
