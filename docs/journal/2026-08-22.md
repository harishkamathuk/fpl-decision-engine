## Implementation delivery

Three implementation slices were merged into develop on the same day, in a
deliberate delivery sequence where each layer depends on the previous.

### #81: Typed run-record provenance ledger

Replaced manual JSON provenance manipulation with a typed, validated, atomic
run-record interface. Key design decisions:

- **Previous-run authority** uses recorded authority events, never file
  modification time or directory ordering. An explicit `previous_run_id` must
  reference a recorded run; an omitted id resolves the current authoritative run
  for the same (season, Gameweek). Cross-Gameweek lineage requires an explicit
  id (operator choice).
- **Completion semantics** follow #80 literally: completed requires every
  mandatory stage to have a terminal PASS/WARN latest attempt; failed requires
  mandatory execution to have failed. A run that is neither stays provisional.
- **Retry after PASS/WARN is rejected** — stage repeatability belongs to the
  future orchestrator (#84), so the ledger refuses rather than choosing
  semantics.
- **Legacy vs v1** distinguished by `schema_version`: absent records are read
  best-effort with absent fields staying absent; nothing is fabricated.
- **Atomic persistence** via temp file + fsync + `os.replace` with optimistic
  concurrency detection.

Independent review: APPROVE WITH NON-BLOCKING FOLLOW-UPS. Concurrency and
authority-enforcement hardening deferred to #84.

### #83: Immutable Gameweek evidence identity

Implemented evidence identity as a typed v1 Gameweek manifest. Key design
decisions:

- **Semantic SHA-256** covers season/Gameweek, snapshot/provider identity,
  semantic source-as-of time, exact artefact byte hashes, projection content
  identity, forecast generation/effective time and only upstream lineage actually
  supplied.
- **Manifest formatting and key order are non-semantic**; source artefact
  whitespace is part of the exact bytes and therefore changes evidence identities.
- **Acquisition UUID and retrieval timestamps** remain separate provenance.
  Filesystem references locate immutable bytes for audit but do not enter
  semantic identity.
- **Atomic publication** uses the same-filesystem temporary-file plus
  hard-link/no-replace pattern. A concurrent identical winner is idempotent;
  a different-byte winner is rejected.
- **RunRecord schema v1** remains the exact historical #81 wire contract.
  New runs use schema v2 with optional `evidence_identity` binding.

### #82: Deterministic Touchline doctor diagnostics

Added a deterministic, read-only diagnostic suite validating the environment
before Gameweek runs. Key design decisions:

- **Release-isolation trigger**: detached HEAD at a recognised release tag
  marks an immutable worktree; branch checkouts at the same commit remain
  mutable. This resolves the Stage 6 path-resolution brittleness exposed by
  the GW1 rehearsal.
- **Missing state root / required dirs are WARN, not FAIL** — every writer
  auto-creates its roots, so a missing directory never breaks a run.
- **Existing-file consistency**: the state-root existence check mirrors the
  resolution check's verdict rather than emitting a misleading "does not exist"
  when the path resolves to an existing non-directory.
- **Centralised state-root resolution**: a single `_StateRootResolution` is
  shared across all three `paths.*` checks, eliminating TOCTOU and protecting
  against `OSError`/`RuntimeError` on invalid paths.

## Delivery sequencing

The implementation order was deliberate:

1. **#81** provides the provenance foundation (run records, stage tracking).
2. **#83** consumes the ledger interface for immutable evidence identity.
3. **#82** validates the environment against #80's state-root/path invariant.

The rapid delivery cadence was possible because each slice was architecturally
bounded with well-defined interfaces and consumed only the previous layer.

## Project position

Bounded correction pass after independent review, per the now-authoritative #80
confirmation that an immutable release worktree is exactly *detached HEAD at a
recognised release tag* (branch-at-tagged-commit and detached-at-untagged-commit are
ordinary mutable checkouts; dirty-worktree semantics unchanged: clean/dirty ordinary
checkout -> PASS/WARN, clean/dirty immutable release worktree -> PASS/FAIL).

- **Centralised state-root resolution** — `DoctorService.run()` now resolves the
  configured state root exactly once into a shared `_StateRootResolution`
  (canonical `Path` or explicit failure); `OSError`/`RuntimeError` (e.g. symlink
  loops) are caught centrally and the single result is consumed by all three
  `paths.*` checks. This removes the unprotected `.resolve()` calls in the existence
  and placement checks (which could previously crash `run()`) and the TOCTOU between
  independently re-resolved checks. A resolution failure is a deterministic FAIL with
  remediation in all three checks; the doctor never raises to the CLI for this class
  of invalid path input.
- **Existing-file consistency** — `paths.state_root_exists` no longer emits a
  misleading "does not exist" WARN when the state root resolves to an existing
  non-directory; it mirrors the resolution check's FAIL ("exists but is not a
  directory"). Resolution owns the type verdict; existence/placement consume the
  shared result.
- **Tests** — added regression coverage for: RuntimeError and OSError resolution
  failures yielding deterministic FAILs (single-resolution reuse verified by counting
  `Path.resolve` calls), existing-file-as-state-root consistency, and detached-HEAD
  without release tag treated as an ordinary checkout (clean -> PASS, dirty -> WARN,
  never FAIL). No existing Stage 6, symlink-containment, sibling-prefix,
  linked-worktree or release-worktree tests were weakened.

No policy semantics changed: the 12 stable check identifiers, deterministic order,
human/JSON contracts, zero-iff-no-FAIL exit, WARN semantics and read-only guarantees
are untouched.

## Issue #84 implementation: resumable Gameweek orchestrator skeleton

Implemented the first bounded Touchline stage machine over the merged #81/#82/#83
contracts. A fresh run records doctor, evidence and baseline as mandatory RunRecord
stages; PASS/WARN predecessors progress, FAIL blocks dependants, and action exceptions
finish the running attempt as FAIL. Successful runs close as completed. Failed runs
remain provisional so explicit resume can append the existing approved retry attempts.

Resume preserves the run ID and completed history, compares season, Gameweek, code
revision and config fingerprint, and verifies the exact already-bound evidence
manifest through the idempotent #83 binding seam before appending any retry. Evidence
or argument drift is rejected without mutation. PASS/WARN stages are skipped; prior
FAIL/BLOCKED stages retry through RunRecordService. A RUNNING attempt is rejected
because #81 has no approved stale-attempt recovery transition.

The CLI command touchline run-gameweek accepts an immutable evidence manifest and
supports explicit --resume. The concrete baseline adapter reconstructs exact snapshot
components through the existing mapper, loads FPL Forecast CSV projections through the
existing adapter, runs the unchanged HiGHS blank-squad baseline, and persists the
existing DecisionRun and content-addressed decision bundle. No orchestration JSON,
history/comparison workflow, scenario lifecycle or optimiser semantics were added.

Focused tests cover success, WARN, doctor/evidence/baseline failure, dependency
blocking, append-only resume, completed-stage skipping, argument/evidence drift,
stale-RUNNING rejection, persistence reload, CLI shape and semantic parity with the
manual HiGHS baseline path.

The control-plane workstream is now anchored by four closed implementations
(#81, #82, #83, #84). The natural next dependencies are #87 (manager-state
acquisition) which unblocks #88 (submission planning safety). The
lineup-evidence validation workstream (#91–#95) is ready for implementation when
the project shifts focus.
