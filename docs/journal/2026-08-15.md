## Decisions

For #4, keep the persistence stack deliberately small and use what the project already has: **Polars + DuckDB**.

- Parquet will be the durable store for curated/derived analytical datasets.
- DuckDB will act as local catalogue/query/control storage: views over Parquet plus small metadata tables such as snapshot catalogue, schema metadata and DecisionRun records.
- Do not duplicate canonical fact rows into DuckDB merely for convenience.
- Do not add PyArrow pre-emptively. Add it only if a focused compatibility or round-trip test demonstrates a concrete gap in Polars + DuckDB.
- Preserve snapshot-grain history rather than destructively replacing current state.
- Use explicit tabular schemas and provenance rather than arbitrary Pydantic serialization.
- Generated Parquet should be written to a temporary sibling path, reopened/validated, atomically promoted, and only then registered in DuckDB.
- Reuse #3's raw snapshot convention exactly; do not create another raw-data layout.

The detailed implementation guidance and OSS reconnaissance are recorded on #4 rather than duplicated here.

## Risks / open questions

The main technical risks to prove early in #4 are type and provenance fidelity rather than scale:

- UUID round-trip representation;
- timezone-aware datetime round trips;
- Money/tenths representation;
- nullable optional fields;
- deterministic `*_latest` view selection without losing history;
- failure atomicity: a failed write must not leave a registered partial dataset;
- schema-version rejection behaviour.

PyArrow remains a deliberate fallback if these tests expose a genuine metadata/type limitation, not a default dependency.

The official FPL access position also remains intentionally conservative. #18 is closed because the research task is complete, not because automated extraction has been approved.

## Deferred deliberately

For #4, do not introduce Delta Lake, Iceberg, a general migration framework, hosted/cloud storage abstractions or a broader data-platform framework. They add complexity without solving the current local decision-engine problem.

## Issue #4 implementation findings

Issue #4 now provides the local persistence slice described above. Canonical teams, players,
gameweeks and fixtures are written as one immutable Parquet file per source snapshot below the
existing season-partitioned `data/curated` layout. DuckDB stores only catalogue, schema and
DecisionRun control metadata, with history and deterministic latest views reading the Parquet files
directly. The Issue #3 raw layout was reused without adjustment.

Polars 1.43 and DuckDB 1.5 handled every required round trip: UUIDs as canonical text, instant-valued
timestamps as UTC-aware microsecond timestamps, Money as exact integer tenths of a million pounds,
enums as their stable string values, relationships as UUID text and nullable fixture/source fields as
nulls. **PyArrow was not needed and no dependency was added.**

The write path uses a temporary sibling Parquet file, reopens it to validate its explicit schema, row
count and integer `schema_version`, promotes it without overwriting prior evidence, and only then
commits catalogue metadata and refreshed views in one DuckDB transaction. A failure removes files
created by that attempt and leaves no registered partial dataset. Unsupported future curated or
DecisionRun versions fail explicitly; rebuild-from-raw remains the evolution strategy.

One local driver quirk surfaced: fetching DuckDB `TIMESTAMPTZ` values as Python objects attempts to
load optional `pytz`. Control-table readers therefore cast timestamps to ISO text and reconstruct
aware standard-library datetimes, avoiding an unnecessary dependency; Parquet timestamps and SQL
time semantics remain timezone-aware.

The main follow-up risk is catalogue-view refresh cost as snapshot counts become large because each
view currently lists registered files explicitly. That is acceptable for the local first slice; measure
before replacing it with broader glob or manifest-driven discovery. There were no deliberate
deviations from the Issue #4 storage architecture or scope. Projection, optimiser, manager-state and
live-source work remain deferred to their own issues.
