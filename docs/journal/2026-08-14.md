# 2026-08-14

## Context

The project moved from the idea of an FPL helper/agent into a more deliberate open-source **FPL decision engine**. The important shift was to avoid making an LLM the decision-maker. Instead, the project should have explicit forecasting, strategy, optimisation and explanation layers that can evolve independently.

The working principle that emerged is:

> **Models forecast. Optimisers decide. Agents explain and interrogate.**

A second useful formulation is:

> What might happen? → forecast. What do I value? → strategy. What action best satisfies it? → optimiser. Why? → agent.

The project repository is `harishkamathuk/fpl-decision-engine`.

## Decisions made today

### Architecture owns the domain

External projects and providers must map into types/contracts owned by this repository. Their schemas should never become the project's domain model simply because they are convenient.

This should allow us to change forecast sources, storage and solvers without redesigning the application.

### External open-source projects sit behind adapters

The default order is:

1. consume an upstream project unchanged if practical;
2. contribute upstream for small fixes;
3. fork only if we genuinely need to maintain behavioural changes;
4. reimplement only when the algorithm is useful but direct dependency is inappropriate.

Avoid copying other repositories into this monorepo and avoid Git submodules by default.

### Human-in-the-loop execution

The engine should recommend actions, not automatically execute FPL transfers. Automatic mutation of the FPL account is not currently considered a competitive advantage and creates unnecessary operational/terms risk.

### Local-first analytical platform

The design is intentionally larger than a script but smaller than enterprise infrastructure.

Current direction:

- Python;
- `uv` / `pyproject.toml`;
- DuckDB as the local analytical/query layer;
- Parquet as durable analytical storage;
- Polars primarily for dataframe work;
- HiGHS/MILP for optimisation;
- Typer CLI;
- Pydantic/configuration;
- pytest/Ruff/Pyright/GitHub Actions.

No Kubernetes, services architecture or hosted database unless a real future requirement appears.

### Time and provenance are first-class

A future recommendation should be reproducible months later. The engine therefore needs to preserve:

- source snapshot/version;
- when information was published/observed/processed;
- effective configuration;
- forecast provider/model version;
- optimiser settings;
- code revision;
- random seed/simulation settings where relevant;
- resulting recommendation.

This also matters for honest backtesting: information must be filtered by what was knowable before the deadline, not merely by event date.

### Projection uncertainty should not collapse to one number

Although early optimisation may use mean expected points, the canonical model should be able to retain richer uncertainty such as expected minutes, start probability and distributions/percentiles when a provider supplies them.

This matters later for captain variance, rival-aware strategy, mini-league win probability and Monte Carlo simulation.

### Strategy is separate from forecasting

The long-term target is not simply "maximise expected points" in every situation.

The same forecasts should eventually support strategies such as:

- maximise expected points;
- protect a mini-league lead;
- chase a leader by seeking useful variance/differentials.

That logic belongs in a utility/strategy layer above forecasting and below optimisation.

## FPL data-source discovery

Issue #18 surfaced an important distinction: **technically public JSON is not the same thing as permission for automated extraction**.

Current official FPL-shaped resources are technically reachable for the core data we need, including bootstrap/static-style data and fixtures. However, the official Terms page currently served is still labelled 2025/26 even though the 2026/27 game is live, and those published terms contain an automated-access/extraction prohibition.

Decision for now:

- do not silently assume an unofficial JSON endpoint is an authorised API;
- do not enable recurring automated official-FPL extraction in Issue #3 while this remains unresolved;
- build the ingestion architecture **offline-first and source-neutral**;
- support raw snapshot/file import through the same provider boundary that a future permitted network source can use;
- keep live snapshots local and ignored rather than redistributing them in the open-source repository;
- use synthetic source-shaped fixtures in CI.

This makes the design slightly more conservative but also cleaner: network acquisition and data interpretation are separate concerns.

## Issue #3 — ingestion design prepared

Issue #3 was expanded into a Codex-ready specification.

The initial vertical slice will support something like:

```text
fpl sync --source snapshot --input <directory-or-manifest>
```

The raw local convention is planned as:

```text
data/raw/<provider>/<season>/<snapshot-id>/
  manifest.json
  bootstrap-static.json
  fixtures.json
```

Snapshots are immutable and content-hashed. Re-importing identical bytes is idempotent; conflicting bytes at an existing snapshot identity must fail rather than overwrite evidence.

Canonical identities should be deterministic and provider IDs remain external references. Numeric provider IDs must not be assumed stable across seasons.

## Issue #4 — storage design prepared

The intended storage split is deliberately simple:

```text
data/
  raw/       # immutable source evidence
  curated/   # canonical normalized Parquet
  derived/   # forecasts/features/optimisation/evaluation
state/
  fpl.duckdb
```

Parquet remains the durable analytical representation; DuckDB is primarily the query/catalog/run-metadata layer rather than a second copy of every large fact dataset.

Generated outputs should be written atomically: temporary output → validation → promote → register. Failed runs must not leave apparently valid partial datasets.

## Issue #5 — projection-provider research

Two open-source options were particularly useful to investigate.

### FPL Forecast (`daniel-mehta/fpl-forecast`)

This project is actively publishing 2026/27 work and its public projection shape aligns unusually well with our needs, including fields such as:

- expected points;
- expected minutes;
- appearance probability;
- start probability;
- probability of scoring 5+ points;
- player/team/position/price context.

Its software licence is AGPL-3.0. Rather than taking a code-level dependency into this MIT repository, the current plan is to support its **projection output as a local file format through an adapter**. This preserves separation and avoids making its implementation part of our codebase.

### OpenFPL (`daniegr/OpenFPL`)

OpenFPL is MIT licensed and interesting if we later decide to run our own forecasting pipeline. It requires more upstream feature/data construction and is therefore not the fastest first projection provider.

### Current #5 order

1. project-owned generic local CSV projection provider;
2. FPL Forecast CSV adapter consuming user-supplied/local projection output;
3. retain OpenFPL as a future run-the-model-ourselves candidate.

Missing optional projection fields must remain missing rather than being invented simply to populate the richer canonical model.

## Process decisions / lessons

### Issues: enough structure, not a second hobby

A recurring risk is over-engineering the project-management system instead of the FPL engine. The current rule of thumb is to create issues for meaningful vertical slices or architectural work, not for every small code change.

No elaborate Projects board, story points, label taxonomy or release bureaucracy unless it starts solving an actual coordination problem.

### AI review is optional, not mandatory ceremony

We briefly explored CodeRabbit/Devin-style independent review and successfully triggered GitHub Copilot review once. For the current project size this felt like unnecessary process overhead.

Current standard: green CI plus a sensible PR review is enough. Add stronger review tooling if the project/code risk later justifies it.

### Chat vs Codex

This chat is working well as architecture/PM/review/control-room context. Implementation-heavy slices such as live/provider I/O, DuckDB, solver integration and repeated test/debug cycles are better suited to Codex with a real local checkout.

The intended handoff point remains Issue #3. Its specification has deliberately been made precise enough that Codex should implement rather than invent architecture.

## Risks / open questions

- **Official FPL access terms:** the currently published terms are season-mismatched and restrictive around automated extraction. Recheck before enabling any automated official-source mode.
- **Operational live source:** we still need a source strategy that is both technically practical and appropriate to use for regular refreshes.
- **Projection artifact reuse:** consuming locally supplied FPL Forecast output is architecturally clean, but any future automated retrieval of published artifacts needs its own source/usage check.
- **Source schema drift:** unofficial/undocumented source shapes can change; adapters and synthetic contract tests should make failures explicit rather than silently corrupt mappings.
- **Cross-season identity:** deterministic provider-season identity is enough for #3, but robust cross-season player/team reconciliation will be required later for modelling/backtesting.
- **Repo metadata typo:** the GitHub repository description has previously shown "Fantary Premier League". It is cosmetic but should be corrected in repository settings when convenient.

## Musings worth preserving

- The competitive advantage should come from better forecasts + optimisation + strategy, not from automating the final button click on the FPL site.
- Rival-aware optimisation should eventually optimise something closer to **probability of winning the mini-league**, not just raw expected points. Early season these objectives may look similar; late season they may diverge materially.
- Global ownership and *effective ownership among the actual rivals who matter* are different signals.
- Multi-gameweek planning should value transfer optionality. A player who is marginally worse this week may be strategically better if the move preserves future flexibility.
- Backtesting recommendations purely on realised points is dangerous. A good decision can lose to variance; the system should eventually measure whether a decision was rational given information available at the deadline.
- "Notebook discovers; library implements" remains a useful rule when modelling work begins.
- The first truly useful milestone is not a polished dashboard. It is roughly Issue #7: the engine can inspect a real manager state and recommend transfers using projections and a legal optimiser.

## Issue #3 implementation — offline snapshot ingestion

Implemented the first concrete ingestion slice on `feature/3-fpl-data-ingestion`. The operational path is deliberately local-only: `fpl sync --source snapshot --input <directory-or-manifest>` reads a complete bootstrap/fixtures pair, validates and canonicalises the entire dataset, then atomically promotes exact source bytes and a versioned manifest under `data/raw/<provider>/<season>/<snapshot-id>/`. No HTTP client or live official-FPL acquisition mode was added.

### Implementation decisions

- Kept raw-byte storage, FPL-shaped source schemas, canonical mapping, provider exposure and application orchestration in separate modules. The application use case consumes `PlayerDataProvider`; source models remain inside the infrastructure adapter.
- Validate both source objects and perform canonical mapping before snapshot promotion. Invalid JSON, incomplete resources, relationship errors, domain invariant failures and season mismatches therefore cannot leave an apparently successful snapshot.
- Snapshot identity combines the UTC observed timestamp with a deterministic content hash. Manifests record per-object SHA-256, byte size, original and stored names, provider, season, observed/imported/processed times, optional source publication time and optional code revision.
- Re-importing the same identity and bytes returns the existing manifest without changing its original import time. Existing evidence with different hashes or bytes fails explicitly and is never overwritten.
- Internal UUIDv5 identities include provider, season, entity type and external ID. Season scoping is intentional because numeric FPL identifiers are not assumed stable across seasons; true cross-season reconciliation remains deferred.
- The season guard derives `YYYY-YY` from the earliest gameweek deadline and checks any supplied manifest season before writing. This is the narrow local equivalent of the useful rollover protection observed in `TopMarx/fpl`; none of its fetch or per-player pipeline was copied.
- Exact availability and news fields remain preserved in raw evidence. The foundational `Player.active` flag is true only for source status `a`; non-available status or news produces a warning rather than a new injury ontology.
- CI coverage uses only small synthetic FPL-shaped files. The CLI integration test replaces socket creation with a failure to prove the path requires no network access.

### OSS reconnaissance applied

The earlier conclusion remains unchanged: implement the project-specific snapshot path locally, use `TopMarx/fpl` only for manifest completeness, raw/derived separation and season-guard ideas, and keep FPL-Core-Insights as an optional current-season cross-check rather than a dependency. Its fixture relationship discrepancy (`teams.code` in current fixtures despite documentation saying `teams.id`) reinforces strict relationship validation at adapter boundaries. No OSS FPL package, dataset or client was added as a runtime dependency.

### Unresolved questions

- Issue #18 remains open: source acquisition and permission for recurring official-FPL access are unresolved, so `refresh` is reserved and non-operational.
- Directory input without a manifest uses the newest required-file modification time as `observed_at`; operational users should supply a manifest when an authoritative observation or publication time is available.
- Cross-season player and team reconciliation remains for later historical/modelling work.
- Availability may eventually need a dedicated evidence model under Issue #10 rather than relying on the coarse canonical `active` flag plus raw source preservation.

### Validation

Ruff and strict Pyright passed. The full offline pytest suite currently contains 28 passing tests. In this WSL desktop environment, plain pytest capture needs the inherited Windows `TEMP` and `TMP` variables removed so Python uses native `/tmp`; this is an environment-specific capture-filesystem issue, not a test network or application dependency.
